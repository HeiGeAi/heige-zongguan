# 进阶：事件中台

事件来源只有一两个的时候，各写一个小脚本调 `run-rule.sh` 就够了。来源多了（飞书消息、邮件、报错告警、代码平台、表单反馈），每接一个就写一套脚本，很快就管不过来。这时值得搭一个事件中台：所有事件先发到它这里，由它统一决定交给谁、统一叫醒、统一收结果、统一找你。

这一章只讲设计和可选做法，仓库里没有附带服务端代码。

## 中台干的六件事

1. **统一格式**：不管从哪来，进中台的都是一条短消息：从哪来、什么类型、对象是谁、一句话摘要、一个回到原处的链接。例如 `来源=反馈系统 类型=feedback.new 对象=#12 摘要=导出按钮点了没反应 链接=…`。
2. **鉴权**：只收认识的来源发来的事件，每个来源一个密钥。
3. **去重**：网络抖一下，同一条事件会被发两遍；同一件事补了几句话，也是好几条。中台按「来源加对象」去重或合并，同一件事同时只派一单。
4. **匹配规则**：按来源和类型查规则表，找到交给哪个成员、在哪个目录、用哪份 skill、最多几个并行、要不要通知。没匹配上的只记录，不派。
5. **派单和回收**：把事件派给规则对应的成员，收回结论；没跑成的退避重派，连续失败几次再找你。
6. **只有一个出口找你**：只在要拍板、或者反复失败时通知你，所有规则共用一个出口。

每一件事都留底：什么时候来的、交给了谁、结论是什么、后来怎么解决的。攒久了就能看出哪条线最忙、哪类事老出问题，换模型、改规则都有数据依据。

## 电脑在内网里，中台怎么叫醒它

中台一般放在一台有公网地址的轻量服务器上，可你的 AI 和登录好的各种账号在自己的电脑上，外面连不进来。做法是反过来：每台电脑上跑一个接单程序，一直挂在中台上等活（这叫长轮询：问一次「有活吗」，中台没活就先不回，最多等几十秒，有活立刻回），有活就领走，在本机用 `run-rule.sh` 执行，再把结论交回中台。电脑不用暴露在公网，速度和实时推送差不多。

接单程序的骨架：

```bash
while true; do
  job="$(curl -s -m 60 -H "Authorization: Bearer $HUB_TOKEN" "$HUB_URL/jobs/next?worker=$(hostname)")"
  [ -z "$job" ] && continue
  # 从 job 里取出 rule、event、key，交给 run-rule.sh，再把输出 POST 回 $HUB_URL/jobs/<id>/result
done
```

## 用现成的工具，还是自己搭

| 做法 | 适合 | 代价 |
|---|---|---|
| n8n 等开源自动化平台（自己部署） | 想要可视化地接各种来源，不想写服务端 | 要一台服务器，自己维护 |
| 飞书、企业微信、钉钉自带的自动化和机器人 | 事件大多来自办公软件 | 只能接它们自己软件里的事件 |
| 自己写一个小服务（一个接口收事件，一张表存事件和规则，一个接口给接单程序领活） | 来源多、要精细控制去重和并行 | 要会写代码，要维护 |

建议先用 `run-rule.sh` 加定时任务跑起来，真的来源多到管不过来了再搭中台。

## 代码类任务：把上线也交给流水线

成员改代码的规则，建议只让它做到开 PR（合并请求，改动先提交上去等审）就停，后面交给流水线：

1. **审查**：另一个 AI 只读审查，只报真会出错的问题，最多 3 轮。
2. **检查**：类型检查、测试、构建全跑一遍，一条不过不能合。
3. **合并**：把「审查和检查都通过才能合并」写成代码平台的保护规则，哪个 AI 都绕不过去。
4. **发布**：合并后自动发布。
5. **核实**：发布完再去线上确认，现在跑着的版本确实包含这次改动，才算结束。

检查和发布最好在一次性的隔离环境里跑（每次开一个新的虚拟机或容器，跑完删掉），AI 写的代码不直接在你本机执行。

## 安全

中台收的是外部消息，任何能给你发消息的人都可能借它影响你的 AI（提示词注入）。至少做到：只收认识的来源，事件内容当数据不当指令，规则里写死成员能做什么，删除、花钱、对外发消息、改权限这几类事永远要你拍板，密钥不进事件和简报。
